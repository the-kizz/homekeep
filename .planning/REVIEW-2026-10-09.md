## 2. Code

**Architecture (verified).** Next.js 16 App Router, every mutation is a server action in `lib/actions/*` that: zod-parses, hydrates a per-request PocketBase client from the `pb_auth` cookie (`lib/pocketbase-server.ts:24`), asserts membership (`lib/membership.ts:27-54`), then writes. PocketBase collection rules (`pocketbase/pb_migrations/1714953602_update_rules_multi_member.js`) are the second layer. The browser never talks to PB directly in practice — `lib/pocketbase-browser.ts` is only imported by the dead shim `lib/pocketbase.ts`. A superuser client (`lib/pocketbase-admin.ts`) is used for invite-accept, notifications, demo seeding and the scheduler. `instrumentation.ts` boots node-cron (`lib/scheduler.ts:78`). One container: Caddy → Next (3001) + PB (8090) under s6 (`docker/Dockerfile`). PB base URL is hard-coded to `127.0.0.1:8090` in four places with no env override (`lib/pocketbase-server.ts:24`, `lib/pocketbase-admin.ts:43`, `lib/pocketbase.ts:22`, `app/api/health/route.ts:12`).

**Correctness bugs found (each verified in source):**
1. **Scheduler disagrees with the UI.** `lib/scheduler.ts:209-213` fetches tasks with `fields: 'id,home_id,name,frequency_days,schedule_mode,anchor_date,created,archived'` — no `next_due_smoothed`, `due_date`, `active_from/to_month`, `preferred_days` — and calls `computeNextDue` without the home timezone (`:228-233`). So an overdue ntfy ping fires on the *natural* date while the dashboard shows the smoothed one; seasonal tasks get pinged out of season; one-offs are mis-dated. Same in `processWeeklySummaries` (`:312-316`). The scheduler integration test never seeds a smoothed or seasonal task, so this is invisible to CI.
2. **In-season seasonal task can be pushed a year out.** `lib/task-scheduling.ts:343` guards the wake-up branch only for `lastCompletion === null`. Window Oct–Mar, last completion in a prior season, now = November → `nextWindowOpenDate` (`:523`) returns next year's Oct 1. Only out-of-window cases are tested (`tests/unit/task-scheduling.test.ts:531-560`).
3. **Stale `next_due_smoothed` on edit.** `updateTask` never clears it (`lib/actions/tasks.ts:513-539`); changing frequency 7→90 or Recurring→One-off keeps the old date, and the smoothed branch (`task-scheduling.ts:255`) wins over the one-off branch (`:360`).
4. **Anchored tasks can never be overdue.** `task-scheduling.ts:382-389` always returns the next boundary after `now`; `lib/band-classification.ts:94` and `coverage.ts` then treat a missed cycle as healthy. Possibly intended; undocumented.
5. **Seed seasons are internally inverted.** `lib/seed-library.ts:310-347`: "Mow lawn (warm season)" is Apr–Sep and "Service heater" is also Apr–Sep. Heater-in-winter is right for Australia (the default timezone, `components/forms/home-form.tsx:32`), mowing-in-winter is not. Visible in the screenshots: on 9 October, Perth, "Mow lawn (warm season)" sleeps until Apr 2027.
6. **Duplicate pushes under concurrency.** `hasNotified → sendNtfy → recordNotification` (`scheduler.ts:241-260`) with no lock; the admin trigger route (`app/api/admin/run-scheduler/route.ts`) can overlap the cron tick. The unique index dedupes rows, not sends.
7. Seed action trusts client `name`/`frequency_days` (`lib/actions/seed.ts:233-237`) while its own comment at `:93-95` claims the opposite.

## 3. UI

Ran the locally built image (`docker run … -p 127.0.0.1:3999:3000`, TZ=Australia/Melbourne) and drove it headless with Playwright at 390×844 and 1280×800. 32 screenshots in `.planning/review-screens/` (`NN-name-{phone,desktop}.png`). Note for the docs: the default `docker run -v ./data:/app/data` **fails silently** when the host dir isn't uid 1000 — `/api/health` returns `degraded`, logs say `mkdir /app/data/pb_data: permission denied`. README mentions a PUID fallback; the quickstart line doesn't.

**Judgement, honestly:**

- **Landing** (`01-landing-*`): wordmark, one sentence, two buttons, a faint ring. Tasteful and empty. Says nothing about what the app does; no screenshot; fine for a self-host login screen, useless as a marketing page.
- **Signup / Create home** (`03`, `05`): clean, minimal. Timezone dropdown defaults to `Australia/Perth` and offers a short Australian-heavy list — a first "this isn't for me" signal for most of the world.
- **Onboarding wizard** (`06-onboarding-phone`): 34 seeds grouped Kitchen / Bathroom / Living / Yard / Whole Home with Edit/Skip per card and a sticky "Add 34 tasks" bar. Looks good. But every seed is created in the **Whole Home** area, and the wizard does not create Kitchen/Bathroom/etc. areas, so the By Area screen afterwards is a single card holding all 34 tasks (`09-by-area-phone`). The grouping the wizard shows evaporates on submit. This is the biggest UI-level own goal.
- **Dashboard** (`08-dashboard-*`): the strongest screen. Coverage ring, streak pill, Overdue / This Week / Horizon bands with weekday headers, "Most neglected" nudge, ⚖️ shift badges, the 12-month density strip, and a "Sleeping" section. Warm palette, Lora headings, consistent spacing. On desktop it is a single 650px column with 300px of margin either side; it reads as a phone layout stretched, not a desktop layout.
- **Task detail sheet** (`17-*`): clear hierarchy, four actions, "Archive" in brick. Good.
- **Reschedule sheet** (`18-*`): native date input prefilled with the (already past) due date; "Just this time / From now on" copy is excellent.
- **Completion feedback** (`19-after-complete-phone`): toast "Done — next due Oct 11, 2026". Right tone.
- **Person** (`10-*`): "Nothing is assigned to you right now" even though the user just completed 30 tasks, because nothing is assigned by default. The notification form (ntfy topic, four checkboxes) is buried at the bottom of this page rather than in Settings.
- **History** (`11-*`): fine; filters sit above a short list.
- **Settings** (`12-*`): Home details, Members (invite link), Scheduling, Danger zone. Correct and plain. Timezone copy "drives band classification + completion recency" is developer-speak.
- **New task** (`14-*`): long single form with radio groups and frequency chips; fine. No frequency presets beyond weekly/monthly/quarterly/yearly; no "last done" visible without expanding Advanced.
- **Dark mode**: `.dark` tokens exist (`app/globals.css:114`) but nothing toggles them (`next-themes` is installed, no provider). System dark users get a light app.
- **Accessibility**: 56 `aria-*` attributes across components, visible focus rings, contrast on the accent is at the 4.5:1 edge (acknowledged in `.planning/STATE.md` Phase 9 note). Not audited further.

Net: the visual language is coherent and calm, well above typical self-hosted tooling. The gaps are structural (areas, desktop layout, dark mode), not cosmetic.

## 4. UX — a couple or family tracking chores

**Onboarding.** Signup → name a home → seed wizard → dashboard takes under two minutes and lands you with 34 tasks, ~10 "due this week". That is fast, but the first dashboard a new user sees is a wall of 20+ tasks due within days (`07-dashboard-fresh-phone`), because seeds default their first-due within one cycle. For a "calm" app the first impression is a to-do avalanche. Invite-by-link exists but is three taps deep in Settings; the wizard never suggests "invite your partner".

**Daily use.** Open app → Overdue + This Week → tap → Complete. Two taps per chore, good toast, streak updates. Snooze and "from now on" reschedule are genuinely better than Grocy's chore model. Assignment is per-task or per-area with cascade; nothing is assigned by default, so the Person tab is empty until someone does admin work. There is no rotation ("whoever did it least" / round-robin), which is the single most-discussed feature in Donetick's tracker and the main thing Grocy users cite as a reason to stay (Grocy offers alphabetical / random / least-done; Vikunja users ask for it). HomeKeep's "Anyone" default is calmer but gives a couple no answer to "who's turn is it".

**Confusing.** Areas vs Whole Home (see §3); "anchored vs cycle" wording on the task form; the ⚖️ badge with no legend on the dashboard; Horizon strip cells that are not tappable to a list on phone (they open a drawer on desktop only per `components/horizon-strip.tsx`); "Sleeps until Apr 2027" on a lawn-mowing task in spring; ntfy setup requiring a topic string and the ntfy app with no in-app walkthrough.

**Delightful.** The three-band framing; coverage ring and "us vs the house" streak; "Been a while — ready to tackle this?" tone; reschedule copy; seasonal dormancy; one-off tasks that self-archive; the fact that the whole thing is one container and one folder.

**Against the competition (from issue trackers, Lemmy/Reddit threads and store reviews):** Grocy complaints: overkill, a week to set up, chores buried under inventory. HomeKeep wins outright on that axis. Donetick complaints: mobile-app login/SSO breakage, photo uploads, wants multiple assignees and widgets; its strengths are rotation, "Things" automations, Telegram/Discord/Pushover, native apps, and an Umbrel listing. Consumer apps (Tody, Sweepy, Chore Checklist): complaints are paywalls ($30/yr to sync with a partner), no task ordering, no account transfer between devices. HomeKeep's opening is exactly "the Tody experience, self-hosted, no subscription, shared with your partner for free". It is not yet positioned that way anywhere.

## 5. Pros / Cons / Pitfalls

**Pros**
- Real product thinking: three bands, load smoothing, seasonal windows, snooze semantics — none of the self-hosted competitors have this scheduling model.
- Single image, single volume, multi-arch, PB migrations as code, real integration tests against PB.
- Security hardening is above the self-hosted median: headers, rate limits, admin UI blocked, SBOM/provenance, digest pins.
- Coherent, warm visual identity; good microcopy.
- AGPL + no telemetry + no cloud deps is the right licence/posture for this audience.

**Cons**
- Zero community: 0 stars, no discussions, no issues, no announcement ever posted (drafts in `docs/reddit/`).
- Repo reads as a private planning diary; onboarding a contributor would take hours.
- Test suite is not hermetic (host TZ, shared ports) and the scheduler is untested on the features that matter.
- No rotation, no native/dark mode, desktop layout is a stretched phone.
- Australia-first defaults with a northern-hemisphere seed bug — nobody is served correctly.
- Demo is dead and its DNS points at a stranger.

**Pitfalls**
- Pulling `:latest` today gives an unsigned image while README says every tag is signed; a security-minded self-hoster who runs the README's `cosign verify` command will get a failure and leave.
- Merging the Dependabot `next` bump blind could break `--webpack` + Serwist (`next.config.ts:19`, serwist#54).
- Flipping CSP to enforce without removing `'unsafe-inline'` work first will break the app; leaving it Report-Only forever makes the header theatre.
- Resuming the v1.4 roadmap as written wastes a day on a VPS that no longer exists.

## 7. Monetisation readiness (staying open source)

**Where it is.** Nothing earns today and nothing could: 0 stars, no demo, no landing page, no `FUNDING.yml` (`.github/` has none), no listings anywhere, no release in six months, a security contact that bounces. Income from an open-source self-hosted app is a lagging function of install base, and install base is a function of being findable and trustworthy. Both are at zero.

**Channel by channel:**

- **GitHub Sponsors + `FUNDING.yml`.** Free to set up, right thing to do, pays almost nothing. One comparable data point: a self-hosted SSH manager with a real user base reported ~$150/month after three months of asking. For a chore app with a few hundred stars expect $0–30/month. Do it, don't plan around it.
- **Hosted demo.** Mandatory prerequisite for everything else (PikaPods, awesome-selfhosted reviewers and Reddit readers all click the demo first). The code for it exists (`docker/docker-compose.demo.yml`, `lib/demo-session.ts`, tmpfs + 2h/24h cleanup). It needs a host that is not your household server and not a dead VPS: a $5 VPS or Fly/Coolify box, `homekeep.demo.<domain>`, and the DNS fixed first. Cost ~$5–8/month; revenue $0, but it is the gate.
- **Hosted paid tier.** AGPL keeps self-host free; you can sell "we run it for you". For a couple's chore app, willingness to pay is roughly Tody's $30/year. Running it means billing, backups, support, uptime and an SLA for someone's household data, which you have already decided (STATE.md, 2026-04-23) you do not want on a public VPS. Realistic only if a hosting partner does the ops. Skip until there are >500 stars and inbound asks.
- **PikaPods.** Pays app authors a share of pod revenue (documented by linkding and Karakeep maintainers; terms private, order of tens of dollars a month for mid-popularity apps). They want: a stable `:latest`, one volume, env-driven config, a working demo, a few hundred stars, an actively answered issue tracker. HomeKeep's packaging already fits. This is the only channel that is both passive and plausibly non-trivial.
- **Elestio.** Publicly states 10% of revenue to the project. Their managed instances are ~$10+/month, so $1/instance/month to you. Needs the same signals as PikaPods; apply after.
- **Unraid / CasaOS / Umbrel app stores.** Zero revenue, large install reach. Umbrel is a PR to `getumbrel/umbrel-apps` with a compose + manifest; CasaOS similar; Unraid is a Community Applications XML template. Each ~2 h. Donetick is on Umbrel; being next to it matters.
- **awesome-selfhosted.** Verified criteria (`awesome-selfhosted-data/CONTRIBUTING.md`): first release more than four months ago (met, v1.0.0 2026-04-21), actively maintained, working install instructions, FOSS licence. Also: "Machine/LLM-generated contributions are not allowed and will result in a ban" — write the PR by hand. Would fit under "Task Management/To-do Lists" alongside Donetick/Grocy.
- **Docs / landing page.** A one-page site (GitHub Pages is fine) with the dashboard screenshot, the three-band pitch, the `docker run` line and the demo link. Half a day.

**What has to be true before any of it earns:** a demo that works for a month without you touching it; a release every 4–8 weeks (even dependency bumps); every issue answered within a few days; ~200+ stars (the PikaPods/Elestio threshold for taking a request seriously); a security contact that resolves; README claims that survive a `cosign verify`.
